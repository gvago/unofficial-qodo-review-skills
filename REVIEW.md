# Review wording

Write review findings like a teammate explaining a bug in plain English.
Start the description with what goes wrong for the user, in one short sentence.
Then explain the triggering condition and cause in one or two short sentences.
Use everyday words, active voice, and short sentences. Avoid abstract phrasing and long chains of function names.
Keep the main description under 60 words where possible. Put detailed code tracing in the evidence, not the opening sentence.
Keep exact identifiers only where needed to locate or explain the bug. Preserve the precise trigger, impact, and suggested fix.
Do not change the review schema, severity criteria, or which bugs you report. Change only how you explain them.
